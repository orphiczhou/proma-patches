## 三、对照基线（必须有的参照）

产品级指标无基线则无意义。设两条基线：

1. **vs 裸 prompt（无 tree-system）**：同一个任务，用「直接指挥多个 agent + prompt 约束」跑一遍，记录速度/成本/质量。tree-system 应在**质量**和**成本可控**上显著优于（速度可能持平或略优）。
2. **vs Layer 1 only（有会话管理，无纪律层）**：用 Layer 1 工具但不用 tree-system 的门禁/审计/护栏。tree-system 应在「伪完成拦截 / 成本爆炸防护」上显著优于。

> ⚠️ **当前 gap**：两条基线都**未采集**。v1 需要专门设计对照实验（3-5 个典型任务 × 3 种模式）。

## 四、反指标（不该增长的，增长=失败）

| 反指标 | 含义 | 目标 |
|---|---|---|
| 成本爆炸次数 | macp2 型（create_session 滥用 / 无收敛） | = 0 |
| 安全失守次数（BYPASS） | audit-attacks 测试出现 BYPASS | = 0（当前 18 攻击 0 BYPASS ✅） |
| 文档与引擎失同步 P0 | 历次审计抓出的 P0 类问题 | 下降趋势 |
| 纸面门禁（形式有实战无） | 中期评价的「死硬约束」 | 下降趋势 |

## 六、数据采集 gap（诚实声明）

当前 success-metrics 的多数指标**没有数据**，因为：
1. **无真实团队使用**：tree-harness 仅研究者自用（n=1），无团队级数据
2. **无对照基线**：未设计裸 prompt / Layer1-only 对照实验
3. **未向 Proma 提交 PR**：维护者维度数据为 0
4. **缺使用埋点**：tree-state 记录的是执行数据，未聚合为产品指标（如「伪完成拦截率」需从 audit_log 聚合）

**v1 补采建议**：
- 设计 3-5 个典型任务 × 3 模式（裸 prompt / Layer1 / tree-system）对照实验
- 从 tree-state 聚合产品指标（建树完成率 / 拦截率 / 成本分布）
- 向 Proma 提交首个 PR，启动维护者维度数据

## 七、成功定义（一句话）

> **tree-harness v1 成功 = 关键补丁被 Proma 合并（维护者维度）+ 真实团队在典型任务上验证多 agent 比单 agent 更可靠更可控（团队维度）——两者都需数据支撑，而非主观判断。**
