## 重大问题（必须修，阻断 v0.1 发布）

### M1. 自动备份机制彻底失效（spec §A.1 / §8.3 承诺但代码不工作）

- **文件**：`workspace-files/.context/trees/tree-state.js:284-316, 416`
- **现象**：实测连续 15+ 次写入后，`<tree_id>/` 目录下没有任何 `tree-state.backup.*.json` 文件生成。
- **根因**：`writeState` 在序列化前 `delete cleanState.__write_counter`（line 285），导致 `__write_counter` 永不落盘；每次命令进入 `withLock → readState` 都从磁盘读出 `state.__write_counter = undefined`，于是 `(undefined || 0) + 1` 永远 = 1，`1 % 10 !== 0` 永不触发备份。
- **影响**：spec §A.1 / §8.3 把"每写 10 次自动备份"列为铁律，§9.2 v0.1 必做项第 9 条；这是 F3 灾难恢复（tree-state 损坏）的最后一道防线。无备份 = F3 不可恢复。
- **修复建议**：把写入计数器序列化到磁盘（如 `state._meta.write_count`），或在 `.lock` 旁维护 `write.count` 文件；不要用"内存字段"做需要持久化的判断。

### M2. 无 milestone 的 leaf 仍允许 `set-status done`

- **文件**：`tree-state.js:677-690`
- **现象**：实测 `leaf add → leaf set-status done`（中间未加任何 milestone）成功返回 `ok:true`。代码注释（line 687-689）自承"宽松处理：允许无 milestone 直接 done（用于简单测试场景）"。
- **根因**：spec §3.5 / §A.5 要求"切到 done 时校验所有 milestones 都 audit_pass=true"。但代码把"无 milestone"当作"无问题通过"，等于让 `milestones=[]` 直接绕过校验。
- **影响**：子 Agent 自评里把这个明确列为"已知的潜在问题"——确实违反 spec，但 spec 原文措辞有歧义（"所有 milestones"在空集上 vacuously true）。建议补一条"milestones 必须非空才能 done"或显式 spec 注释。
- **修复建议**：要么修代码加非空校验，要么在设计文档 §A.5 显式说明"空 milestone 集合允许 done"。
- **指挥官决策**：按"严格路径"修复——空 milestone 集合不允许 done。理由：契约精神，milestones 是子会话工作的骨架，没有骨架就不能宣告完成。与元原则"工程化 = 拆成执行片段"一致。

### M3. `E_STATUS_INVALID` 错误码定义但从未使用

- **文件**：`tree-state.js:77` 定义，`tree-state.js:665` 用 `assertEnum` 抛 `E_SCHEMA_INVALID`
- **现象**：实测 `leaf set-status nanju leaf-x invalid_status` 返回 `E_SCHEMA_INVALID` 而非 spec §A.1 承诺的 `E_STATUS_INVALID`。
- **影响**：spec §A.1 明确把 `E_STATUS_INVALID`（status 不在枚举内）和 `E_SCHEMA_INVALID`（输入 JSON 不符合 schema）分开；调用方做错误处理时无法区分。
- **修复建议**：`cmdLeafSetStatus` 改用 `assertEnum(new_status, STATUS_ENUM, 'status', E_STATUS_INVALID)` 或在 `assertEnum` 增加可选错误码参数。

## 中等问题（建议修，可在 v0.1 后期补）

### S1. 命名正则放行过多边界 case

- **文件**：`tree-state.js:63`
- **现象**：实测 `NANJU-ROOT`（全大写 prefix）、`A-eval`（缺 prefix 段）、`nanju--eval`（连续两个分隔符）都被 `MATCH`。正则 `(\w+)` 允许任意大写字母、下划线、数字组合，spec §6.5 表格里写明 prefix "4-8 字符，全局唯一"（如 nanju/sweng/webv3，暗示小写）但未给硬正则约束。
- **影响**：tree-commander §12 命名规范未强制 prefix 长度（4-8），可能产生 `n-root` 或 `nanju-of-very-long-name-root`。
- **修复建议**：`prefix` 段改为 `[a-z][a-z0-9_]{3,7}`，明确大小写与长度；或在 design doc 注明"prefix 规范仅为约定"。

### S2. `nowIso()` 输出依赖运行机器时区

- **文件**：`tree-state.js:114-129`
- **现象**：函数依赖 `d.getTimezoneOffset()`。如果脚本部署在 UTC 容器（如 CI 跑），输出的 ISO 字符串会是 `+00:00`，与 spec §8.1 示例（`+08:00`）不一致。设计文档 §A.1 没强制时区。
- **影响**：跨时区部署时 `--since` 过滤、备份文件名时间戳等可能产生不一致；属轻微。
- **修复建议**：要么 spec 注明"时区跟随系统"，要么硬编码 `+08:00`（如设计示例所示）。

### S3. Windows 下原子 rename 在目标文件被占用时会失败

- **文件**：`tree-state.js:301-308`
- **现象**：代码已捕获并清理 tmp，但 spec §A.9 v0.1 acceptance 要求"Windows 兼容"。Windows 上 `fs.renameSync` 当目标 `tree-state.json` 被另一进程持有读/写句柄时会失败（`EPERM`）。这是 Windows 文件系统的固有差异，单次 `try/catch` 清理 tmp 后会丢失本次状态更新。
- **影响**：在并发场景（即使有锁）+ 外部读工具同时打开 `tree-state.json` 时可能误判。
- **修复建议**：Windows 下重试 3-5 次（带退避），或改用 `fs.renameSync` 替代策略（先 `unlinkSync` 目标再 rename，虽非原子但 Windows 行为更稳定）。

### S4. tree-worker §6 与 tree-commander §6 的字段命名不完全对齐

- **文件**：`tree-worker/SKILL.md:230-246` 的 plan 模板字段名 `sub_missions[].est_steps`；`tree-commander/SKILL.md` 没有列 plan 上行字段，只在 §7 路由表提到 `event: plan`。
- **影响**：tree-commander 路由 Agent 时若不读 tree-worker 的字段定义，可能漏接 `est_steps` / `silence_ack_seconds` 等元数据。属轻微。
- **修复建议**：tree-commander §7 加一行"plan 上行字段定义见 tree-worker §3.2"。

### S5. 备份文件命名可能在 < 1ms 内连续备份时撞名

- **文件**：`tree-state.js:352` 用 `Date.now()`（毫秒）+ `safeLabel`。两次连续 `backup --label same` 在同毫秒内会覆盖。
- **影响**：实战中极罕见（自动备份每 10 次写触发，间隔远 > 1ms），可忽略。
- **修复建议**：在文件名加 `process.hrtime.bigint()` 后缀或随机段。

## Q1-Q5 逐项回答

### Q1：tree-state.js 是否符合附录 A 的 spec？

**大部分符合，3 处不符**（见 M1/M2/M3）。所有子命令实现齐全（验证：dispatch 表共 21 个 case，spec §A.3-A.7 列出 21 个命令，全部覆盖）。命名正则、枚举校验、原子写入（tmp+rename）、并发锁（`openSync(wx)` + 10s 过期清理）、双写 drift_log/drift_history 全部到位。问题集中在：自动备份计数器失效（M1）、空 milestone done 绕过校验（M2）、`E_STATUS_INVALID` 未使用（M3）。

**子 Agent 报告的两个修正验证**：
- 正则 bug 修正：✅ 验证通过，§6.5 全部 6 个示例（含根 `nanju-root`）匹配，5 个负例（`A-eval`/`nanju-`/`-nanju`/`nanju-A-`/`nanju-A-eval-iX`）正确拒绝。**但 `NANJU-ROOT`、`nanju--eval` 被错误放行**（见 S1）。
- "无 milestone done 允许通过"是真实问题（见 M2），子 Agent 自评诚实，但应该被当作 spec 违规而非"宽松处理"。

### Q2：tree-commander SKILL.md 是否符合设计？

**符合**。4 条铁律（§1）措辞强硬（"严禁"、"必须"），4 件套契约模板（§6）5 段 YAML 完整，事件路由表（§7）覆盖 5 类事件，三档纠偏决策树（§8）含递进条件，命名规范（§12）含正则，灾难恢复（§10）4 类故障齐全。v0.1 待启用能力（§9）明确说"不要求执行心跳/内审/竹节"，符合 §9.3。工作流程（§4）落到 `tree-state.js` 子命令级别。**唯一遗漏**：§7 `plan` 路由没说默认放行后 verdict=nack 走中档纠偏要调哪个子命令（应补 `leaf autonomy-override`）。

### Q3：tree-worker SKILL.md 是否符合设计？

**符合**。9 条铁律覆盖 brief_echo 强制（铁律 1）、milestones 列举（铁律 2）、自审（铁律 3，v0.1 可选）、`.note.md`（铁律 4）、上下文最小化（铁律 5）、self_check 必附（铁律 6）、YAML 上行（铁律 7）、禁直接读写 tree-state.json（铁律 8）、autonomy 边界（铁律 9）。4 类上行模板（§3.1-3.4）字段完整。`.note.md` 模板（§5）含 `chose`/`reason`/`review_trigger`。§4 内审明确标 "v0.2 启用，v0.1 可选"。禁止行为清单 12 条覆盖直接读写 tree-state.json。**唯一遗漏**：§3.4 blocked 模板字段 `wait_for: "decision"` 没说明根会话回应字段（如 decision 字段），子会话收到后不知道怎么 parse。

### Q4：两个 Skill 之间是否一致？

**基本一致**。4 件套字段定义双方一致（brief/dod/report/autonomy/self_audit 都有）。上行消息格式双方一致（4 种 event 类型 + YAML）。tree-commander §5 引用的所有 tree-state.js 子命令都在 .js 里实现了（验证：dispatch 表全覆盖）。命名规范双方都引用 §6.5，正则一致。**轻微差异**：tree-worker §3.3 done 模板有 `milestones[].audit_pass/note_path`，tree-commander §7 路由表里 done 验收 Agent 没明说会读这两个字段（隐含通过 deliverables + self_check 传递，可补一句）。

### Q5：是否有 bug、安全漏洞、未覆盖的边界？

**有**。M1（自动备份失效）是阻塞性 bug。S3（Windows rename 失败处理）是潜在可用性问题。其他：
- **并发锁**：实测 stale lock 清理工作正常（mtimeMs > 10s 时 unlink 重试）。
- **路径处理**：全用 `path.join`，跨平台 OK；但 `nowIso()` 时区依赖运行环境（S2）。
- **错误路径覆盖**：所有 dispatch 分支都有 default 抛 `E_UNKNOWN`，覆盖完整。
- **JSON 注入**：所有 JSON 参数都走 `parseJsonArg`（`JSON.parse` 严格模式），无 eval 风险。
- **tree_id 路径穿越**：`tree-state.js:172` 用正则 `/[\\/\s]/` 拒绝路径分隔符，OK；但没拒绝 `..`、`%`、Unicode 控制字符。属轻微。

## 验收建议

**不能直接进入 v0.1 测试阶段**。必须先修 3 个重大问题：

1. **M1**（自动备份失效）：5 行代码修复（把 write_count 落盘）。不修则 F3 灾难恢复路径不可用，整个体系最后一道防线失效。
2. **M2**（空 milestone done）：在 §A.5 spec 里二选一明确措辞，并相应修/不修代码。
3. **M3**（错误码区分）：1 行代码修复。

修复后建议跑 3 个核心回归用例：
- **R1**：连续写 11 次，确认 `*.backup.*.auto.json` 生成。
- **R2**：`leaf add → leaf set-status done`（无 milestone），确认按 spec 行为拒绝/允许。
- **R3**：`leaf set-status <invalid>`，确认返回 `E_STATUS_INVALID`。

修完 + 跑过 R1/R2/R3 → 可进入 v0.1 测试。S1-S5 可在 v0.1.1 补，T1-T4 延后到 v0.2。
