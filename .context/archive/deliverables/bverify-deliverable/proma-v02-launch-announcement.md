## 引言

AI Agent 正在从"能对话"走向"能交付"，但这条路上的挑战远比想象中复杂。单会话模型在长链路、多分支任务中面临三大结构性瓶颈——上下文膨胀导致信息丢失、方向漂移让产出偏离目标、质量不可控使得每次交付都像开盲盒。

Proma 树形会话执行体系的诞生，正是为了系统性地解决这些问题。v0.1 阶段，我们完成了从理论到原型的关键跨越：树形拓扑调度、5 件套契约、事件通道、9 条铁律——一套将复杂任务分解为子会话并行协作的工程框架被成功验证。

今天，站在 v0.1 的肩膀上，我们正式宣告 v0.2 启动。如果说 v0.1 回答了"能不能做"，那么 v0.2 的使命是回答"做得好不好"。本文档将从成就回顾、版本宣言、技术详解和迁移指南四个维度，全面呈现 v0.2 的全貌。

## 一、v0.1 成就回顾

v0.1 虽然定位为原型验证，但交付的成果远超"跑通"二字。以下四项核心产出构成了树形会话执行体系的基础骨架：

### 1. tree-state.js — 状态管理引擎

`tree-state.js` 是整个体系的唯一真相源（Single Source of Truth）。它负责管理树形会话的拓扑结构、节点状态、事件日志和版本历史。v0.1 中，它实现了以下关键能力：

- **树拓扑管理**：支持节点的增删改查、父子关系维护、路径定位（如 `A/B1/C2`）
- **事件日志记录**：所有上行事件（brief_echo、done、blocked、plan）的结构化持久化
- **版本追踪**：每次状态变更自动递增版本号，支持回滚查询
- **自审记录**：milestone 级别的自审结果写入，为 v0.2 的质量追踪打下基础

技术选型上，我们采用 JSON 文件持久化 + 内存缓存的混合架构，兼顾了可靠性和性能。文件锁机制保证了多会话并发写入时的数据一致性。

### 2. tree-commander SKILL — 指挥官操作手册

`tree-commander` 是根会话（指挥官）的标准化操作指南。它定义了：

- **任务分解规范**：如何将用户意图分解为 5 件套契约（brief / dod / report / autonomy / self_audit）
- **Fork 调度策略**：何时 Fork 新子会话、如何分配 leaf_id、命名规范
- **事件响应协议**：对 done / blocked / plan / brief_echo 四种上行事件的标准处理流程
- **竹节交接机制**：当子会话上下文超 85% 甜点时，如何无缝创建接力会话

v0.1 期间，tree-commander 成功调度了 S1 全链路测试——从根会话 Fork 出多个子会话，每个子会话独立完成各自的篇章撰写任务，最终由汇总会话整合为完整文档。整个过程中零信息丢失、零方向漂移。

### 3. tree-worker SKILL — 工人操作手册

`tree-worker` 是子会话（工人）的标准化操作指南，也是 v0.1 中迭代最密集的模块。它定义了：

- **9 条铁律**：从"首条消息必须是 brief_echo"到"严禁直接读写 tree-state.json"，每一条都来自实践中踩过的坑
- **4 种上行消息模板**：done / blocked / plan / brief_echo，全部结构化 YAML，确保指挥官路由 Agent 能解析
- **5 件套契约解读流程**：工人如何理解 brief / dod / report / autonomy / self_audit，明确"能做什么"和"必须请示什么"
- **上下文最小化规则**：不留一次性大输出、不重复读已读文件、超 85% 主动声明

tree-worker 的设计哲学是"约束即自由"——给工人足够清晰的边界，反而最大化其自主决策空间。

### 4. S1 全链路测试 — 从理论到实证

S1 测试是 v0.1 的验收里程碑。它模拟了一个真实场景：为 Proma 项目撰写一份 v0.2 启动公告（即你正在阅读的这份文档的创作过程本身，就是一次树形执行的真实演练）。测试链路如下：

```
根会话（指挥官）
  ├── A: v0.2 具体技术细节（由 B 提供上下文）
  ├── B: v0.1→v0.2 迁移指南
  ├── C: 公告核心正文（本文档）
  └── F: 文档整合与最终发布
```

S1 测试验证了整个体系的端到端可行性：契约下发、子会话 Fork、独立执行、事件上报、结果汇总——每一个环节都按设计运行。更重要的是，它暴露了 v0.1 的两个关键缺陷——内部自审可跳过、上行消息格式不统一——这些发现直接塑造了 v0.2 的优化方向。

---

**v0.1 总结**：4 项核心产出，1 次全链路验收，9 条铁律沉淀。原型验证阶段正式关闭。

## 二、v0.2 启动宣言

### 为什么是现在？

v0.1 证明了树形会话执行体系的可行性，但可行性不等于可用性。S1 测试中暴露的问题不是边缘案例，而是系统性问题：

- **质量不可追溯**：v0.1 的内部自审是"建议执行"而非"必须执行"，导致工人可以跳过自查直接上报 done。这意味着指挥官收到的 done 事件缺少质量保证——无法区分"真正完成"和"声称完成"。
- **偏差不可量化**：当工人的产出与原始任务存在偏差时，v0.1 没有机制记录和传递这些偏差。指挥官只能在最终汇总时被动发现——而此时返工成本已最大化。
- **上下文不可持续**：v0.1 的上下文最小化依赖工人自觉，缺乏系统级的强制执行和监控。

这些问题不是 bug，而是 v0.1 作为原型的天然边界——它的设计目标就是"跑通"而非"跑稳"。现在"跑通"已验证，启动 v0.2 的时机已经成熟。

### v0.2 要达成什么？

v0.2 的主题是 **"从可行到可靠"** 。我们将在 v0.1 的骨架之上，铺设三条核心能力管线：

#### 管线一：内部自审必须化（铁律 3 升级）

v0.1 铁律第 3 条从"建议"升级为"必须"——每个里程碑完成后，工人必须经过独立审计环节进行对齐校验，审计结果写入 milestone 记录。最多自纠 2 次，2 次后仍不达标则标记偏差并声明上报。

这一升级的实质是**将质量检查从指挥官的外部职责内化为工人的自觉动作**，让质量保证嵌入执行流程而非依赖事后审查。

#### 管线二：双层纠偏机制

v0.2 引入路线图 Agent（plan → 路线图匹配）和哨兵 Agent（上下文甜点监控 + 竹节强制交接）两层独立纠偏：

- **路线图 Agent**：在 brief_echo 阶段校验工人的理解是否与任务计划一致，在方向偏差升级前发出预警
- **哨兵 Agent**：自动监控所有活跃子会话的上下文使用率，超过 85% 甜点自动触发竹节交接，确保长链路任务不因上下文膨胀而丢失关键信息

双层纠偏的架构决策是：**路线图 Agent 管"对不对"，哨兵 Agent 管"撑不撑"**——两者独立并行，互不耦合。

#### 管线三：偏差追踪与可视化

v0.2 为每个 worker 引入偏差声明机制——当工人产出与原始契约存在偏差时，必须在 done 上报中明确声明。tree-state.js 对应扩展 drift 记录能力，支持按时间线追踪偏差的发现、分类和处置全过程，为指挥官提供子任务质量的趋势评估和未来的拓扑可视化数据基础。

### 不变的内核

尽管 v0.2 引入了大量新机制，但树形会话执行体系的内核不变：

- **5 件套契约**仍然是任务下发的基本单位
- **9 条铁律**仍然是所有工人的行为底线（第 3 条升级，其余 8 条延续）
- **4 种上行事件**仍然是上下行通讯的唯一通道
- **tree-state.js** 仍然是唯一真相源

v0.2 不是推倒重来，而是在已验证的骨架上加固肌肉。

## 三、v0.2 技术能力详解

### 1. 心跳通道（Heartbeat Channel）

**设计意图**

v0.1 仅有事件通道——子会话在完成、卡点或计划拆解时主动向根会话上报。这留下了一个致命盲区：子会话可能卡死、静默或「忘了说」，而根会话对此完全无感知。事件通道回答「正在发生什么」，心跳通道回答「为什么没发生」。两者互补，形成完整的全局感知网。

**工作机制**

心跳通道以 Proma 持久化定时任务（automation）为载体，核心配置如下：

- 调度类型：`interval`，间隔 15 分钟
- 会话模式：`reuse`（复用同一个心跳子会话，保留巡检上下文）
- 权限模式：`bypassPermissions`（无人值守全自动执行）

每次心跳触发时，按五步巡检流程执行：

1. **拉取活跃叶子**：运行 `tree-state.js leaf list-active <tree_id>` 获取全部 status=active 的叶子及其最近事件时间戳和上下文使用率。
2. **获取最近活动**：对每个叶子调 `mcp__session__list_messages(session_id, limit=3)`，检查最近三条消息的时间戳和内容。
3. **哨兵 Agent 判定**：将叶子列表 + 最近消息输入哨兵 Agent，按判定矩阵输出每片叶子的状态标签。
4. **异常叶子查问**：对「停滞」或「静默」叶子发送 `status_check` 消息，要求其报告当前进度和预计完成时间。
5. **写入心跳日志**：调 `tree-state.js heartbeat append` 持久化本次巡检的全部判定结果。

**哨兵 Agent 判定矩阵**

| 最近活动 | 上下文使用率 | 判定 | 对应动作 |
|---------|------------|------|---------|
| < 5 分钟 | < 85% | 🟢 active | 仅记录，不干预 |
| < 5 分钟 | ≥ 85% | 🟡 sweet_spot_risk | 调度竹节交接 |
| 5 ~ 30 分钟 | 任意 | 🟡 stale | 发送 status_check |
| > 30 分钟 | 任意 | 🔴 silent | status_check + 标记待纠偏 |

**去重规则**

心跳唤起时先过滤：若某叶子最近一次事件在 5 分钟内到达，自动跳过——事件通道能解决的事，心跳绝不重复。反之，事件 5 分钟未到，心跳必须接管。

**设计价值**

心跳通道让根会话从「被动等汇报」变为「主动巡检」，在大规模并行任务树（5+ 活跃叶子）场景下尤为关键。人工逐一检查每个叶子是否卡死在工程上不可行，而心跳通道以每 15 分钟不到 30 次 MCP 调用的成本，实现了全自动全局监控。

### 2. 内部自审必须化（Mandatory Internal Self-Audit）

**设计意图**

v0.1 的设计文档已定义了内部自审（补丁 3：递归自审原则），但在实际执行中是「建议做」而非「必须做」，导致多数会话跳过此步骤，偏差直到外部验收才被发现——纠偏代价显著高于事中拦截。v0.2 将内部自审从可选项升级为铁律（tree-worker 铁律 3），呼应体系的核心元原则：「每一步都有判断」。

**工作机制**

内部自审嵌入到每个里程碑 Mi 的完成流程中，形成闭环：

```
Mi 产出完成
  → 自 Fork code-reviewer 子 Agent
  → 子 Agent 输出对齐判定 {alignment, gaps, severity, suggestion}
  → severity == low: 通过，进入 M(i+1)
  → severity >= mid: 按 suggestion 自纠 → 再次审计
  → 第 2 次审计仍 >= mid: 放弃自纠，标记 drift，声明上报
```

审计 Prompt 模板固定输入四类信息并输出严格 JSON：

- **输入**：当前任务 brief（parent_intent / my_mission / in_scope / out_of_scope）+ dod（deliverables / quality_gates）+ 当前里程碑描述 + 实际产出路径
- **输出**：`{ alignment: 0-100, gaps: ["差距1", "差距2"], severity: "low|mid|high", suggestion: "修正建议" }`
- **检查点**：① 产出是否覆盖 Mi.desc 全部内容；② 是否有偏离 in_scope 的内容；③ 是否达到 quality_gates 最低标准

**自纠上限**

最多自纠 2 次（`max_self_corrections: 2`）。这一上限设计有两个目的：一是防止工人陷入无限自我修正循环浪费时间；二是 2 次自纠仍未达标时，偏差由内部升级到外部——在最终 done 上报中设置 `drift_declaration=true`，让外部纠偏从更高起点介入。

**drift_history 写入**

自纠结果不论成败均记录到 drift_history：
- 自纠成功（修正后 severity=low）：`{kind: production, severity: low, action: self_correct}`
- 仍有偏差（2 次后仍 mid+）：`{kind: production, severity: mid, action: declare}`

### 3. 三档纠偏实现（Three-Tier Correction）

**设计意图**

偏差检测和纠偏执行是两件事。v0.1 已有偏差检测能力（根会话可派 Agent 做验收判定），但纠偏动作依赖人工决策和手动执行——发现偏差后需要人判断「发提示还是剪枝」。v0.2 实现了完整的三档自动化纠偏决策树，让「检测 → 判定 → 执行 → 记录」形成全自动闭环。

**三档定义**

| 档位 | 触发条件 | 执行动作 | 对子会话影响 |
|------|---------|---------|------------|
| **轻档（nudge）** | severity=low；或哨兵发现 stale | 发送提示消息，指出偏差项 | 仅提示，不改变自主权 |
| **中档（limit）** | severity=mid 且 30 分钟内已收过 nudge；或 severity=high 首次 | 发送限权消息 + 调用 `autonomy-override` 缩小自主范围 | 增加 must_ask 项，移除部分 can_decide 项 |
| **重档（prune）** | severity=high 且已有限权记录；或中档限权后再次偏差 | archive 旧会话 + 重新 Fork（带 suggested_fork_from_uuid） | 旧会话归档，新会话从偏差前恢复点继续 |

**决策树**

```text
收到 Agent verdict:
  severity == low:
    → 轻档 nudge

  severity == mid:
    近 30 分钟内该 leaf 有 nudge 记录？
      YES → 升级到中档 limit
      NO  → 轻档 nudge（给一次自纠机会）

  severity == high:
    该 leaf 已有限权（autonomy_overrides 非空）？
      YES → 重档 prune
      NO  → 中档 limit（给最后一次机会）
```

**递进状态持久化**

每一步纠偏动作都通过 `tree-state.js drift append` 写入 `tree-state.json` 的 `leaves[X].drift_history` 数组和顶层 `drift_log`。同一偏差的纠偏历史跨会话持久化——即使根会话重启，递进状态不丢失。核心设计原则：**同一偏差最多给 2 次纠正机会，第 3 次必剪枝**。

**双层纠偏全景**

v0.2 形成了完整的双层纠偏体系：

- **第 1 层（内部/事中）**：每个里程碑完成后自 Fork code-reviewer，自纠最多 2 次。内部 clean → 外部从轻档起；内部 drift → 外部起点抬高，可能直接跳中档。
- **第 2 层（外部/事后）**：事件通道（done 上报时验收 Agent 判定）+ 心跳通道（哨兵 Agent 节奏判定），三档递进执行。

两层叠加，从「事后才发现」变为「每步都在判断」，累计偏差始终可控。

## 四、v0.1 → v0.2 迁移指南

### 迁移前置检查清单

在开始迁移前，确认以下 v0.1 基线状态：

- [x] `tree-state.js` 已部署在 `.context/trees/tree-state.js`
- [x] tree-commander SKILL.md（v1.0）已就位
- [x] tree-worker SKILL.md（v1.0）已就位
- [x] 至少跑通过一次 v0.1 S1 验证（简单二叉树完整闭环）

### 迁移步骤

**第一步：升级 tree-worker SKILL.md**

v0.2 版本的核心变更是铁律 3 从「v0.1 可选」升级为「v0.2 必须」，并新增 §4 完整内部自审流程。操作要点：

1. 确认当前 tree-worker SKILL.md 文件路径为 `<workspace>/skills/tree-worker/SKILL.md`
2. 用 v2.0 版本覆盖（文件头部 `version: 2.0`）
3. 确认新增内容：§4 内部自审流程（含触发时机 §4.1、审计 Prompt 模板 §4.3、处理逻辑 §4.4、drift_history 写入 §4.5）
4. 确认 done 模板新增 `drift_declaration` 必填字段
5. 确认禁止行为清单第 3 条：跳过里程碑自审 → severity=high

**第二步：升级 tree-commander SKILL.md**

tree-commander 需要在 v0.1 基础上新增三块内容：

1. **三档纠偏执行流程**：从收到 verdict 到 nudge/limit/prune 的完整决策树，含验收 Agent prompt 骨架
2. **心跳 automation 配置模板**：含完整 YAML 配置和五步巡检流程说明
3. **哨兵 Agent prompt 模板**：含判定矩阵和 JSON 数组输出格式

**第三步：创建心跳 automation**

在工作区下通过 automation MCP 工具创建持久化心跳任务：

- `name`: `tree-heartbeat-<tree_id>`
- `scheduleType`: `interval`
- `intervalMinutes`: 15
- `sessionMode`: `reuse`
- `permissionMode`: `bypassPermissions`
- `prompt`: 按五步巡检流程模板填写

创建后立即执行一次 `run_automation_now` 试跑，确认巡检链路通畅。

**第四步：验证 S3 修复已生效**

检查 `tree-state.js` 中 `writeState` 函数的 rename 调用是否已替换为 `atomicRename`（5 次指数退避，50ms → 400ms）。可通过并发高负载场景验证：连续快速多次写入 tree-state.json，确认无 EPERM 导致的状态丢失。

**第五步：运行 S2 验收测试**

依次验证三个场景：

- **S2a 心跳唤起**：创建 active 叶子后静置超过 5 分钟，确认 automation 触发后 heartbeat_log 有新记录
- **S2b 内部自审**：发起故意轻度偏离 brief 的里程碑，验证 worker 自动 Fork code-reviewer 且 drift_history 产生记录
- **S2c 三档纠偏升级**：模拟 mid 级产出偏差两次（间隔 < 30 分钟），验证第二次触发 limit

### 回滚说明

如果迁移过程出现严重问题：

1. 暂时停用心跳 automation（`active: false`）
2. 回退 tree-worker 和 tree-commander SKILL.md 到 v0.1 版本
3. v0.1 核心闭环不受影响——v0.2 的三个新能力是增强层，非基础层

## 结语与展望

v0.1 回答了"能不能做"——答案是可以。v0.2 回答"做得好不好"——目标是可靠。

从原型到生产，我们走了三个月。这三个月里，4 项核心产出、9 条铁律、1 次全链路测试、2 项关键缺陷发现——每一步都是真实踩坑后的沉淀。v0.2 不是凭空设计出来的，而是被 v0.1 的痛点"逼"出来的：内部自审必须化，是因为我们亲眼看到了跳过自查带来的返工代价；心跳通道，是因为我们发现"沉默不等于正常运行"；三档纠偏，是因为人工判断在多叶子并行场景下根本不可扩展。

展望 v0.3 及更远，树形会话执行体系还有广阔的进化空间：拓扑可视化让整棵任务树的状态一目了然；自适应任务分解让指挥官能根据任务复杂度动态调整树的深度和广度；跨树协作让多个独立任务树之间可以共享中间产出。这些愿景的基础，正是 v0.2 所铺设的可靠执行底座。

感谢每一位在 v0.1 阶段参与测试、提出反馈的团队成员。v0.2，我们继续向前。
