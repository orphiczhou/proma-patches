## 详细攻击场景

### A1 [阻断] QUICKSTART 命令语法与实现完全不兼容

**攻击维度**: 契约边界

**场景描述**:
QUICKSTART.md §3 Step 3 给出的命令:
```bash
node tree-state.js leaf add mydemo-A-draft root "xxx-xxx-A" draft deepseek-v4-pro
```
但 `tree-state.js` 实际的 `leaf add` 子命令签名是:
```bash
node tree-state.js leaf add <tree_id> --json '{"leaf_id":"...","session_id":"...","parent":...,"path":"...","role":"...","model":"...","channel":"..."}'
```
QUICKSTART 使用了位置参数语法（`leaf add <leaf_id> <parent> <session_id> <role> <model>`），但实际实现要求 `--json` 参数。**两者完全不兼容**。

**预期兜底**:
- QUICKSTART 作为"5 分钟快速开始"教程，其命令应可直接复制粘贴执行
- 如果语法错误，tree-state.js 应给出清晰的错误信息引导用户

**实际覆盖情况**:
- ❌ 未覆盖。QUICKSTART 命令无法执行，教程的第一步就失败
- tree-state.js 会返回 `E_SCHEMA_INVALID: leaf requires a subcommand` 或类似错误，但这不能修复 QUICKSTART 中的错误语法
- README.md §5 的 `init` 示例命令格式正确（使用 `--root-brief`），但 `leaf add` 没有在 README 中给出示例

**影响分析**:
QUICKSTART 的存在意义被完全摧毁。用户按照"快速开始"操作的第一步就会失败。这是文档-代码契约断裂的最严重形式。

**漏洞严重度**: **阻断** — 文档声称的入口路径不可执行

### A3 [高] 工人自拆 milestones 与 tree-state.js 记录之间无握手协议

**攻击维度**: 角色视角（工人）

**场景描述**:
Worker SKILL.md §2 规定：如果 self_audit.milestones 未提供，工人应"基于 brief.my_mission 自己拆解"。但 tree-state.js 的 `set-status done` 严格校验要求 milestones 数组非空且全部 audit_pass=true（第 712-728 行）。

攻击路径:
1. 指挥官下发的 5 件套中 `self_audit.milestones` 为空（违反铁律但可能发生）
2. 工人按照 SKILL 要求自己拆解出 M1/M2/M3 并完成工作
3. 工人上报 done，指挥官尝试 `leaf set-status done`
4. tree-state.js 拒绝：`cannot set status=done: milestones must be non-empty`
5. 工人已经完成所有工作，但系统状态无法标记为 done

**预期兜底**:
- tree-state.js 或指挥官 SKILL 应有"工人自拆 milestones → 指挥官补录 milestone add"的握手流程
- 或者在 brief_echo 阶段就检测 milestones 缺失并阻断

**实际覆盖情况**:
- ❌ 未覆盖。没有从工人自拆 milestones 到 tree-state.js 记录 milestones 的桥接机制
- Commander SKILL.md §4 Step 2.4 提到 "对 self_audit 的每个 milestone 调 milestone add"，但这是在"下发子会话"时执行的。如果指挥官忘记这一步，整个链条断裂
- tree-state.js 只保护"写入时"的一致性，不保护"流程中"的一致性

**影响分析**:
工人完成工作但无法标记 done，导致系统状态与实际进度脱节。恢复需要人工介入重新录入 milestones，破坏了自动化流程。

**漏洞严重度**: **高** — 流程断裂点，无自动恢复路径

### A4 [高] tree-state.js 不强制执行审计方法论的 leaf 数下限

**攻击维度**: 角色视角（审计员）

**场景描述**:
tree-audit-methodology.md §铁律 1 要求"指挥官必须 Fork 不少于 4 个子会话执行阶段一"和"不少于 2 个子会话执行阶段二"，并明确声明"只用 1 个子会话审查 → 审计不可采信，必须重做"。

但 tree-state.js 的 `validate()` 函数（第 1210-1329 行）只检查 5 项:
1. parent 引用完整性
2. drift_history fork_to 引用完整性
3. session_id 全局唯一性
4. leaf.path 与 leaf_id 的 path 段一致性
5. milestone.id 同 leaf 内唯一性

**没有任何检查涉及 leaf 数量下限或方法论合规性**。

攻击路径:
1. 审计员只 Fork 1 个子会话做"审查"
2. tree-state.js validate() 返回 `{"ok":true,"issues":[]}`
3. 方法论铁律被绕过，但系统给出"一切正常"的假象

**预期兜底**:
- validate() 应对审计类 tree（可通过 audit_meta 或 leaf role 识别）检查 leaf 数量下限
- 或至少发出警告

**实际覆盖情况**:
- ❌ 未覆盖。方法论要求的强制执行完全依赖人工纪律，无技术手段兜底
- tree-audit-methodology.md §五 的检测方式 "tree-state leaves < 7" 是人工检查清单项，不是代码逻辑

**影响分析**:
审计质量的关键保障（多Agent并行审查）可以被轻易绕过而不触发任何告警。这削弱了整套审计方法论的强制执行承诺。

**漏洞严重度**: **高** — 方法论强制力名存实亡，关键质量门无自动化兜底

### A6 [高] "已知限制"系统性包装未实现功能

**攻击维度**: 结论逻辑

**场景描述**:
README.md 列出 6 项"已知限制":
1. notify 异步上报**未验证**
2. 心跳机制**仅方案**
3. 内审/三档纠偏**仅方案**
4. 竹节交接**仅方案**
5. 并发竞态（实际 bug）
6. 频道兼容性（基础设施问题）

分析这 6 项的实质:
- #2, #3, #4 不是"限制"，而是**未实现的功能**
- #1 是**未验证**（功能可能存在但未测试）
- #5 是**实际 bug**
- #6 是**外部依赖问题**

将 3 个未实现的功能称为"已知限制"是一种修辞策略，使版本看起来比实际更完整。"限制"暗示功能存在但有边界条件；"未实现"意味着功能根本不存在。

**预期兜底**:
- 未实现功能应标注为"v0.3 计划"
- "已知限制"应只包含已实现但有边界条件的功能

**实际覆盖情况**:
- ❌ 未覆盖。术语使用存在系统性偏差
- CHANGELOG 中这些项目的描述也是"仅方案未编码"，但放到 README 时变成了"已知限制"
- README 底部有"下一步（v0.3 计划）"列表，与"已知限制"中 #2-#4 高度重叠，说明作者自己也意识到这些是未实现功能

**影响分析**:
版本完整性被系统性高估。"已知限制"这个词给读者一种"功能存在但要注意边界"的假象，但实际是"功能还不存在"。

**漏洞严重度**: **高** — 成熟度信号系统性偏差

### A8 [中] tree-state.js 事件类型枚举比 worker SKILL 更宽松

**攻击维度**: 契约边界

**场景描述**:
tree-state.js 的 `EVENT_TYPE_ENUM`（第 68 行）包含 8 种事件类型:
```
done | blocked | plan | brief_echo | heartbeat_reply | nudge | limit | status_check
```

Worker SKILL.md §7 禁止行为 #10 规定:
> 禁止使用 done/blocked/plan/brief_echo 之外的事件类型

但 tree-state.js 的 `event append` 接受全部 8 种类型。如果工人错误地使用了 `nudge`（属于指挥官侧事件类型），tree-state.js 会正常接受。

攻击路径:
1. 工人在压力/混淆下发送 `event: nudge` 而非 `event: blocked`
2. tree-state.js 的 `assertEnum` 通过，事件被记录
3. 指挥官的事件路由表不处理来自工人的 `nudge` 事件
4. 工人的实际需求（需要帮助）被静默忽略

**预期兜底**:
- tree-state.js 应区分"工人可发送的事件类型"和"指挥官可发送的事件类型"
- 或在 worker SKILL 加载时校验

**实际覆盖情况**:
- ⚠️ 部分覆盖。worker SKILL 在文档层面禁止了，但 tree-state.js 没有代码层面的强制执行
- 这是"信任工人会遵守规范"的设计，而非"使工人无法违反规范"的设计

**影响分析**:
契约约束仅存在于文档层面，代码层面无强制执行。在大规模部署中，工人的意外违规不会被系统拦截。

**漏洞严重度**: **中** — 契约边界在代码层存在绕过路径

### A9 [中] v0.1"原型验证" vs v0.2.0"初始版本" — 版本叙事矛盾

**攻击维度**: 结论逻辑

**场景描述**:
CHANGELOG.md:
- `v0.2.0 (2026-06-19) — **初始版本**`
- `v0.1（2026-06-18）— **原型验证**`

语义分析:
- "初始版本" (initial version) 理应指第一个正式版本
- "原型验证" (prototype verification) 暗示 v0.1 只是验证原型，不是正式版本
- 但如果 v0.1 只是原型验证，它不应该作为独立版本号出现在 CHANGELOG 中
- 如果 v0.1 是一个真正的版本，v0.2.0 不能是"初始版本"

可能的解释:
- v0.1 是内部原型（未发布），v0.2.0 是首次公开发布
- 但 CHANGELOG 中将两者并列，且 v0.1 有完整的"核心交付"清单

**预期兜底**:
- 一致的版本叙事：要么 v0.1 是首个版本（"初始版本"应为 v0.1），要么 v0.1 不算正式版本（不应出现在 CHANGELOG 中作为独立版本条目）

**实际覆盖情况**:
- ❌ 未覆盖。两个版本的标签自相矛盾
- 可能的 reader 困惑："v0.1 到 v0.2 之间发生了什么？为什么跳过了 v0.1 作为初始版本？"

**影响分析**:
削弱版本历史的可信度。如果连版本标签都不一致，CHANGELOG 中的其他声称也应受到更严格的审查。

**漏洞严重度**: **中** — 信任侵蚀，但不影响功能

### A10 [中] "已验证"场景统计 — 三个场景不等价

如果加权计算:
- 真实环境验证: 2/3（B 和 L2），其中一个有条件通过
- 清晰通过的真实环境验证: 1/3（L2）
- 模拟测试: 1/3（S1）

README 的不加权呈现给读者"3 个独立验证全部通过"的印象，实际情况是"1 个清晰通过 + 1 个有条件通过 + 1 个模拟测试"。

**预期兜底**:
- 应区分"模拟测试"和"真实验证"
- 应区分"清晰通过"和"有条件通过"

**实际覆盖情况**:
- ❌ 未覆盖。README 的呈现方式抹平了验证强度的差异
