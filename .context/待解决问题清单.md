## ISS-001 `remote_create_session` 不传 workspace_id 时默认用调用方工作区 slug，跨实例调用必失败

- **状态**：🟢 已解决（2026-07-04，validateWorkspaceId slug→id 兼容 + remote_create_session 问目标实例 default 兜底）
- **严重度**：中（影响所有跨实例会话创建，但不破坏数据，有明确规避方法）
- **类型**：MCP 接口设计陷阱 / 文档缺口
- **发现日期**：2026-07-03

### 现象
调用 `mcp__remote-session__remote_create_session` 创建远程实例（如 Pro）会话时，若不传 `workspace_id` 参数，必报错：
```
E_WORKSPACE_NOT_FOUND: workspace_id "proma" not in workspace index.
Valid ids: <目标实例自己的 workspace_id>。Use list_workspaces to see all.
```

### 根因
该工具在未传 `workspace_id` 时，默认取**调用方当前工作区**的 slug（本工作区是 `proma`）作为目标远程实例的 workspace_id。但远程 Pro 实例的工作区索引里**没有** `proma` 这个 slug（Pro 只有自己的默认工作区，id 形如 `eb5e3f9c-…`），因此必然找不到。

工具 help_hint 提示「Use list_workspaces to see all」，但**没有**用目标实例的默认/第一个工作区做兜底——把"该传哪个 id"的负担完全丢给了调用方，且默认值在跨实例场景下永远错。

### 规避方案（当前必做）
跨实例创建会话前，**先调 `remote_list_workspaces(instance=<目标>)` 拿到目标实例自己的 workspace_id，再显式传入** `remote_create_session(workspace_id=...)`。

### 理想修复（待 patch）
在 `remote_create_session`（及同类 remote_* 写操作）中：当未传 `workspace_id` 时，自动调用目标实例的 `list_workspaces` 取**第一个/默认工作区**兜底，而不是套用调用方 slug。

### 实测依据
2026-07-03 20:34 在 Pro 实例（`127.0.0.1:19877`）端到端验证远程会话操作时踩到：
- 不传 workspace_id → 报错 `E_WORKSPACE_NOT_FOUND`（默认用了 `proma`）
- 传 Pro 实例 workspace_id `eb5e3f9c-d16c-419d-afcb-19e89c4114ee` → 创建成功（session `4e1e8e26`），后续 `remote_send_message`（GLM-5-turbo 准确回复）/ `remote_get_session_context` / `remote_archive_session` 全链路通过。

**附带结论**：Pro 实例远程会话操作整体可用，仅此创建入口的默认值有坑。

## ISS-002 Tree 面板点击同名 title 会话切换失效（navigate-to-session）

- **状态**：🟢 已解决（2026-07-04，备选A 预热 listAgentSessions + 诊断日志 + 失效 toast；title 假设证伪）
- **严重度**：中（影响 tree 面板点击 leaf 切 Proma 会话；仅同名 title 会话场景，日常较少但不便）
- **类型**：UI 交互 bug / IPC 切换链路
- **发现日期**：2026-07-03

### 现象
在 tree 面板（`proma-tree-view.js`）点击 leaf/commander 节点，期望切换到对应 Proma 会话（侧边栏 + 聊天区）。但当两个会话 **title 相同、session_id 不同**时，点击切换不动——目标会话不激活。tree 面板内部 detail 切换正常（用 leaf_id，不受影响）。

### 根因
`navigate-to-session` handler（patches.cjs）已传 `{ sessionId, title }`（与 Proma 内置 `openAgentSession(sessionId, title)` 一致，main.cjs 行 572367），通过 `tray:open-agent-session` 事件让 renderer 切换。补 title 后仍不行，**疑似 Proma renderer 的会话切换/高亮逻辑用 title 匹配 tab**（同名歧义，找第一个），而非纯 sessionId。renderer 在打包 bundle（`index-*.js`），无法直接改。

### 规避方案（当前）
- 同名会话场景手动在 Proma 侧边栏点击目标会话切换
- 或避免给会话起完全相同的 title

### 理想修复（待查）
绕开 `tray:open-agent-session`（带 title，renderer 可能用 title 找 tab），找 Proma **纯 sessionId-based 切换 IPC**：
- 候选 `quick-task:open-session`（main.cjs 行 570190，待验证参数格式 + 是否通用）
- 或 main.cjs 其他 setActive 通道（grep `setActiveTabId` / `open-session` / `activate-session`）
- 验证哪个 IPC 让 renderer 用 sessionId 而非 title 切换

### 实测依据
2026-07-03 20:32 tree 面板改造收尾验证：
- 补 title 前：同名切换不动
- 补 title（`{sessionId, title}`，与 Proma 内置一致）后：**仍不动**（反证 renderer 非因缺 title，疑似主动用 title 匹配）

## ISS-004 Electron 主进程未捕获异常：write EPIPE（socket 写已关闭管道）

- **状态**：🟢 已解决（2026-07-04，bridge 连接级 socket on-error + res.end try/catch + 顶部 uncaughtException 限定 EPIPE/ECONNRESET）
- **严重度**：中-高（主进程 Uncaught Exception，可能致 Proma 卡死/崩溃，影响所有进行中任务）
- **类型**：Electron 主进程稳定性 / 未捕获异常 / 进程间通信
- **发现日期**：2026-07-04
- **触发场景**：nanju 树任务执行过程（多 session 创建 + send_message 通信密集期）

### 现象
Proma 主进程弹窗：`A JavaScript error occurred in the main process — Uncaught Exception: Error: write EPIPE`

```text
Error: write EPIPE
  at afterWriteDispatched (node:internal/stream_base_commons:159:15)
  at writeGeneric   (node:internal/stream_base_commons:150:3)
  at Socket._writeGeneric (node:net:966:11)
  at Socket._write (node:net:978:8)
  at doWrite (node:internal/streams/writable:598:12)
  at clearBuffer (node:internal/streams/writable:783:7)
  at onwrite (node:internal/streams/writable:653:7)
  at WriteWrap.onWriteComplete [as oncomplete] (node:internal/stream_base_commons:105:10)
```

### 根因（已确认，2026-07-04 诊断）
EPIPE = 往**已关闭的对端 socket** 写入。**确切的 EPIPE 源**：`proma-dev-patches.cjs` 的 HTTP bridge server（`createExternalHttpBridge` → `http.createServer`，line 980）。

- bridge server 只有 server 级 `on('error')`（line 1032，处理 EADDRINUSE 等），**连接级 socket 无 `on('error')`**
- handler 是 async（line 1017 `req.on('end', async…)`），处理完用 `res.writeHead` + `res.end`（line 1023-1027）写响应
- 当 MCP 客户端在 server 写响应前断开，`res.end()` 底层 `node:net` Socket write → EPIPE，无 handler → 冒到 process `uncaughtException` → Electron 主进程弹窗
- 全文件无 `process.on('uncaughtException')` 兜底

**触发时序印证**：nanju 树密集调 `mcp__session__*`（`send_message` wait=true 超时 600s）；`proma-mcp-server.cjs` line 75 `req.on('timeout') → req.destroy()` 客户端先超时断开，bridge async handler 仍在等子会话返回，等完 `res.end()` 时 socket 已关 → EPIPE。典型"客户端先断、服务端后写"竞争。

> 注：`proma-mcp-server.cjs` 的 `req.write`（line 76）有 `on('error')`（line 72）兜底，**不是**主进程 EPIPE 源。

### 影响
- 主进程 Uncaught Exception 可能让 Proma 进入异常状态（卡死 / 部分功能失效）
- nanju 树任务执行中断风险（事件丢失 / 状态不一致）

### 修复方案（已拟定 A+B，2026-07-04 用户选"先不改"）

**A 精准**——bridge server 加连接级 socket error handler：
```js
// line 980 createServer 后、listen 前加：
server.on('connection', (socket) => socket.on('error', () => {}));  // 吞 EPIPE/ECONNRESET
```

**B 全局兜底**——patches.cjs 顶部加：
```js
process.on('uncaughtException', (err) => {
  if (err && (err.code === 'EPIPE' || err.code === 'ECONNRESET')) {
    log(`[swallowed] ${err.code} on socket write (client likely disconnected)`);
    return;
  }
  log(`[uncaughtException] ${(err && err.stack) || err}`);
});
```

**推荐 A+B 组合**（A 堵 bridge 连接级，B 兜其他偶发 socket，双层防护）。

### 决策记录
- 2026-07-04：根因诊断完成；用户选"**先不改**"；未来动手时部署范围 = **dev + release dist 都改**（patches.cjs 多份同步），改完重启实例验证。

### 实测依据
2026-07-04 ~11:21 nanju 树任务执行过程报出。call-log 尾部全 `ok:true`（tree 引擎正常），证实报错在主进程 socket 层而非引擎层。无 Proma 主进程日志（`~/.proma/logs`、`~/.proma-dev/logs`、`AppData/Roaming/proma-dev/logs` 均不存在）。

### 实测依据
2026-07-04 ~11:21 nanju 树任务执行过程报出。Proma 主进程日志路径待确认。
