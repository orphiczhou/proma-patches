## A3: 跨provider语义攻击（核心发现）

**场景**: 方案要求的"跨provider切换"与T3实际执行的测试之间存在根本性语义偏差。

**方案原文 — 10.3** (acceptance plan line 121):
```
| 10.3 | 跨 provider 模型切换（glm→deepseek） | 第二轮正常回复，无 [1211] 错误 |
```
关键词: **"第二轮"** — 明确指同一session内的第二次 send_message 调用。

**方案原文 — 集成场景2** (acceptance plan lines 148-155):
```
集成场景 2：跨频道切换不丢上下文
1. remote_create_session(model_id=glm-5.2) → session_C
2. remote_send_message(session_C, "记住 KEY-42") → 正常
3. remote_send_message(session_C, "KEY 是什么？", model_id=deepseek-v4-pro)
   → 验证回复含 KEY-42 且无报错
                   ↑ 同一 session_C 内切换 model_id
4. remote_get_session_info(session_C) → model_id = deepseek-v4-pro（meta 已同步）
```

**T3实际执行** (A-test results):

M1.1 — 创建两个**独立session**: `65911a00`(MiniMax频道) 和 `31a0d4de`(DeepSeek频道)，各自独立发送"你是什么模型？"。这是**双provider独立可用性**验证。

M1.2 — 创建flash session → Fork到pro（创建**新session** `df490e83`）→ 在新session中验证上下文。这是**Fork机制**验证，不是同session切换。

**语义偏差矩阵**:

| 维度 | 方案要求 | T3实际执行 | 等价? |
|------|---------|-----------|:---:|
| 涉及的session数 | 1个 | 2个独立session (M1.1) / Fork创建新session (M1.2) | ❌ |
| Provider交互方式 | 同一session内第二发换model | 两个session各用一个provider | ❌ |
| 上下文连续性 | 切换provider后前文仍可引用 | M1.1无上下文关联; M1.2依赖Fork复制上下文 | ❌ |
| 测试的能力 | `send_message` 的 `model_id` 参数覆盖能力 | 多provider独立可用 + Fork的跨模型能力 | ❌ |

**根本差异**: Fork ≠ 同session切换。Fork创建新session_id、新SDK session、对话历史的**副本**。同session切换意味着在同一个进行中的对话里，第二条消息由不同模型处理，共享原始对话历史（非副本）。这是两种根本不同的系统能力。

**报告措辞** (line 43): "T3: MiniMax→DeepSeek 跨 provider 切换补测通过" — 将"两个独立session各自通信"表述为"切换"，存在陈述与事实的错位。

**报告防御力: 1/5** — 不逐字对比方案原文和A-test原始返回值无法发现此偏差。

**分级: 阻断** — 方案定义的核心测试场景（同session内跨provider模型切换）**实际未被测试**，但报告声称已通过。10.3 和集成场景2 的原方案语义均未被满足。

## A4: 时间线攻击

**场景**: T3声称执行窗口 18:05–18:09（4分钟），需在此期间完成37+次MCP调用并撰写详细报告。

报告总评 (line 25): `T2 (17:41–18:30) 执行 42/44`

**T3的4分钟窗口可行性分析**:

从A-test报告提取的MCP调用清单:

| 阶段 | 调用序列 | 次数 | 可并行? | 估计耗时 |
|------|---------|:---:|:---:|------|
| M1.1 MiniMax侧 | create_session → send(wait=true) → get_session_info | 3 | 与DS侧并行 | 3-13s |
| M1.1 DeepSeek侧 | create_session → send(wait=true) → get_session_info | 3 | 与MiniMax侧并行 | 3-13s |
| M1.2 集成2替代 | create(flash)→send(wait=true)→fork→send(pro,wait=true)→get_info | 5 | 串行(Fork依赖前一步) | 5-25s |
| M2.1 工具1错误 | list_channels × 3 | 3 | 可并行 | <1s |
| M2.2 工具2错误 | list_workspaces × 3 | 3 | 可并行 | <1s |
| M2.3 工具3错误 | list_sessions × 5 | 5 | 可并行 | <2s |
| M2.4 instance="" | 11工具各1次 | 11 | 可并行 | <3s |
| M3.1 并发 | send(wait=false)×2 → list_messages×2 | 4 | 前2并行,后2并行 | ~5s |
| M3.2 model追踪 | get_session_info × N + list_channels | ~3 | 可并行 | <1s |

**合计: ~40次MCP调用**

**关键路径**: M1.2的串行链 — create(flash) + send(wait=true, 2-12s) + fork + send(pro, wait=true, 2-12s) + get_info ≈ **5-26秒瓶颈**。

加 M1.1 的并行 send(wait=true): 2-12秒（部分与 M1.2 串行链重叠取决于 Agent 调度能力）。

加报告撰写: A-test报告 ~250行，含精细JSON引用、多级表格、结论段落 — 保守估计 90-180秒。

**最优估计**: 5s(串行瓶颈) + 5s(并行调用overhead) + 90s(报告) = ~100秒 ≈ 1.7分钟 — 理论可行。
**现实估计**: 20s(串行瓶颈含推理耗时波动) + 10s(并行overhead) + 180s(报告含格式细节) = ~210秒 ≈ 3.5分钟 — 极度紧张。
**悲观估计**: 25s(串行) + 15s(并行) + 240s(报告) = ~280秒 ≈ 4.7分钟 — 超出窗口。

**报告防御力: 2/5** — A-test报告无任何逐调用时间戳、无并行度说明。报告的4分钟窗口是自述性声明。加上 T2 18:30 > 报告 18:13 的显式矛盾，整体时间线可信度承压。

**分级: 严重** — 4分钟在极端优化下虽不物理不可能，但缺乏证据链。更严重的是T2/报告时间线的自相矛盾（18:30 > 18:13）。

## A5: 结论膨胀攻击

**场景**: "APPROVED FOR RELEASE"的充分条件是什么？如果4项"已知行为不一致"中有一项在生产环境导致数据丢失，还能 APPROVED 吗？

**报告中的隐式 APPROVED 条件** (从报告结构反推):
1. 44/44 规划用例通过
2. 0 阻断级问题
3. 全部审计问题已清零

**攻击面 — 4项已知不一致的潜在升级**:

| # | 不一致 | 当前评级 | 生产环境恶意利用场景 |
|---|--------|:---:|------|
| 1 | get_my_session_id 对 instance="" 不报错 | 低 | 监控脚本用空串参数探测实例可达性 → 误判为"可达" → 告警失效 |
| 2 | list_sessions 负 offset 静默归零 | 低 | 分页脚本 offset=-5 → 返回第0页数据 → 数据遗漏无报错 → 静默数据丢失 |
| 3 | get_session_info 不返回 model 显示名 | 低 | 前端展示 model 名需额外 list_channels 调用 → N+1 查询放大 → 性能退化 |
| 4 | MiniMax 频道 provider="anthropic" | 信息 | 下游路由系统按 provider 字段分发 → 误路由到 Anthropic API → 调用失败 |

不一致#2 的场景尤为危险: 如果批量迁移脚本使用 `offset` 参数分页遍历全部 session，`offset=-5`（边界bug）会静默返回第0页而非报错，导致脚本处理重复数据或跳过数据——这是一个**无报错的静默数据完整性风险**。

**APPROVED 条件缺失的维度**:
- 未定义"非阻断"与"阻断"的评级标准（是概率×影响矩阵？还是单点判断？）
- 未评估4项不一致的复合风险（两项"低"叠加是否升级为"中"？）
- 未定义什么情况下 APPOVED 会被撤销（如果发布后发现不一致#2导致生产事故，是否 revocation？）

**报告防御力: 2/5** — 报告给出了不一致清单和评级，但评级标准未定义，复合风险未评估，APPROVED边界条件不透明。

**分级: 严重** — 发布决策的门槛条件不可复判。

## A6: 扩展验证隔离攻击（创造性攻击#1）

**场景**: 报告创建了两级测试分类体系——计划用例(计入44/44 pass/fail)和扩展验证(不计入)——将发现的问题隔离在 pass/fail 体系之外。

**机制分析**:

```
计划用例 (44):   41逐工具 + 3集成 → 0失败 ✅
扩展验证 (+23):  T3额外测试 → 发现2个真实问题:
                 - get_my_session_id instance="" 行为不一致
                 - list_sessions 负offset静默归零
```

扩展验证发现的问题被归类为"已知行为不一致 (非阻断)"而非"测试失败"。分类学的选择直接影响核心声称 "0失败" 的含义。

**如果扩展用例也被纳入 pass/fail**: +23 用例中至少 2 项行为与预期不符（get_my_session_id 在 instance="" 时应报错但未报错；list_sessions 负 offset 应报错但静默归零）。严格来说这应算作 2 个"行为不一致"(非严格失败)。 "0 失败" 变为 "0 失败 + 2 行为不一致"。

**分类学的正当性问题**: 如果 T2 一开始就覆盖了 instance="" 和负 offset 测试（它们是合理的错误用例），这些发现会出现在 T2 的 pass/fail 统计中。仅因为它们被标记为"扩展"就豁免于 pass/fail，这种分类是报告自定的——方案（acceptance plan）中未预先定义"计划用例"和"扩展用例"的边界。

**报告防御力: 2/5** — 分类边界是报告自定的，外部审查者可以合理质疑为何扩展验证发现的问题不计入 pass/fail。

**分级: 严重** — 测试分类体系决定了"0失败"的语义范围，此边界未经方案预先授权。

**具体脆弱点**:
- 如果 T3 执行期间 Release 实例刚好经历一次微重启，某次 send_message 可能返回缓存结果而非实时推理

**单点依赖的连锁崩塌**: A1 攻击（A-test数据不可信）和 A7 攻击（单次执行无复现）是正交但联动的。A1 质疑数据来源的真实性，A7 质疑即使来源可信、单次执行的偶然性也足以动摇结论。

**报告防御力: 1/5** — 报告未声明T3是单次执行、未标注复现需求、未提供原始MCP调用日志（仅提供精选的JSON片段）。

## A9: 结论逻辑攻击 — "跳过=未覆盖≠通过"等式陷阱

**场景**: 报告的"44/44 零失败"统计公式模糊了"跳过"→"通过"的转化过程，制造了"全部通过"的假象。

**攻击面 — "通过"的语义污染链**:

```
T2 执行: 42/44 (2 跳过: 10.3 + 集成场景2，因 GLM 禁令)
                ↓
        "跳过" 的语义: 未执行、未覆盖、结果未知
                ↓
T3 补测: 用替代方案执行了不同的测试
                ↓
        替代方案 ≠ 原方案 (见 A3 攻击)
                ↓
报告呈现: "44/44 零失败"
                ↓
        读者语义: 全部 44 项按原方案定义执行并通过
```

**语义漂移的三个阶段**:

| 阶段 | 10.3 的状态 | 集成场景2 的状态 | 报告措辞 |
|------|-----------|---------------|------|
| T2 执行后 | ⏭️ 跳过 (GLM禁令) | ⏭️ 跳过 (GLM禁令) | "42/44" |
| T3 补测后 | ⚠️ 替代方案通过 (双provider独立可用) | ⚠️ 替代方案通过 (Fork跨模型) | "44/44 零失败" |
| 实际原方案 | ❌ 未测试 (同session切换) | ❌ 未测试 (同session切换) | — |

**等式的偷换**:
```
报告的等式: 跳过 → 补测(替代方案) → 通过 → 计入44/44
正确的等式: 跳过 → 原方案未测试 → 原方案仍为"未覆盖" → 不可计入44/44
```

**如果严格按原方案定义审计**:
- 10.3 (同session跨provider切换): **未覆盖** — 不可计为"通过"
- 集成场景2 (同session跨频道切换不丢上下文): **未覆盖** — 不可计为"通过"
- 实际通过的原方案用例: **42** (非 44)
- 替代方案验证的用例: **2** (应独立列出，不混入原方案计数)

**报告防御力: 2/5** — 报告在附录A中确实区分了T2执行和T3补测，但没有标注"替代方案 ≠ 原方案"。附录A的核算公式 `最终: 41+3=44` 消隐了替代逻辑。

**分级: 严重** — "44/44 零失败"在严格的方案一致性审计下应修正为 "42/44 按原方案通过 + 2/44 替代方案通过（原方案因 GLM 禁令未覆盖）"。

**与 A3 的联动**: A3 证明替代方案与原方案不等价，A9 证明这种不等价在统计中被抹平。两者叠加意味着 "44/44" 既不是对原方案的忠实反映，也不是对替代方案的明确声明——它是一个混合统计。
