## 流程选择

为测试报告选定了 3 条核心流程，覆盖 3 种典型用户角色：

- P1 审批者 — 验证报告的"决策可用性"
- P2 QA — 验证报告的"追溯可用性"
- P3 Oncall — 验证报告的"诊断可用性"

## 关键发现

**P2 高阻塞**: T3 补测原始数据来源不可追溯。报告声称 T3 通过但未给出 session ID、worker leaf ID、原始数据路径。这是回归测试的核心需求 — 如果第三方无法独立验证 T3 数据，整个"44/44 零失败"结论的可复现性存疑。

**P3 高阻塞**: 性能数据是粗粒度聚合（send_message 2-12s），无按工具/provider 分组延迟分布、无超时/retry 记录。对于 oncall 工程师使用报告做故障排查来说不可用。

**P1 中阻塞**: APPROVED FOR RELEASE 依赖单一 worker 的 T3 数据，且总评维度表混入扩展验证项。

## 阻塞程度判断标准

- 高: 该步骤对目标角色是核心需求，报告的缺失导致角色无法完成工作
- 中: 可部分完成但需要大量推断/跳转/拼接信息
- 低: 小不便，可通过简单修改改善

## 触发重审条件

- 报告新增 T3 补测数据追溯信息（session ID / 原始数据路径）
- 性能数据增加按工具分组延迟分布
