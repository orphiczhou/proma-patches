## 四、本轮实战教训

### 4.1 监督 worker 不能只看 status / write_count，必须读 events 详情

nanju05-A-worker 在 17:47:40 已发 `done` event（self_check 13/13 pass），但在 17:49:08 又发 `blocked` event（E_BORROWED_IDENTITY）。**leaf `status` 字段 + tree `write_count` 是长轮查询的"假信号"**：
- worker done 后 status 仍可能是 active（等 commander 派 auditor 调 audit_gate）
- write_count 持续增长（worker 发 done / blocked / brief_echo 都是 write），但不代表 leaf 真正闭环
- **正确姿势**：监督必须 `tree_event_list` 拉 events 数组，看末尾 event 类型 + meta（done / blocked / brief_echo with alignment）

### 4.2 commander 长轮 write_count 假信号问题

root 的 done event（18:07:38）发生在 worker done event（17:47:40）后 20 分钟，期间 commander 一直在做：
- 派 C2-auditor leaf（fork_session 096a71e6）
- 等待 auditor brief_echo + done
- 调 milestone_set_result + audit_gate（worker / auditor 各一次）
- 回填 worker alignment brief_echo（17:54:32）
- 最后 root 自己 done（18:07:38）

期间 `write_count` 持续增长但 worker leaf `status` 未变，**单纯轮询 status 容易误判 worker 卡住**。建议后续 commander 监督策略：长轮时拉 events 末尾事件 + `last_event_type` 双确认。

### 4.3 旧 tree 用旧 SKILL，新 tree 才能验证新协议

nanju04 的 worker 在 2026-07-15 起跑时是旧 SKILL，行为已固化在 tree-state.json 中，事后无法回填新协议。**v0.17.0 验证必须在新启动的 tree 上做**（如 nanju05），不能复用旧 tree。

### 3.4 §4.6 实战生效需要"双触发"

新 SKILL §4.6 文档（worker 主动读 → 自觉 spawn G1-G5）+ 引擎 `audit_meta.review_required=true`（硬强制：无 review_round 不让 done）**二者缺一不可**：
- 只有新 SKILL 而无 review_required：worker 可能偷懒跳过（行为不稳定）
- 只有 review_required 而无新 SKILL：worker 不知道怎么 spawn G1-G5（事件 schema 不对）
- nanju05 实战证明：**双触发 = worker 主动按协议 spawn + 引擎兜底强制 schema 校验**，才能稳定产出合规 `review_round` event

### 4.5 schema 小瑕疵（非阻断）

worker 在 review_round reviewer_session_id 用了占位 UUID（11111111-...），是误用旧 schema 的痕迹。引擎未硬拦（review_round schema 校验只看 perspective / findings 数组 / converged / red_count），但理想状态应填实际 SubAgent session_id。**建议**：v0.17.1 在 SKILL §4.6 加一条"reviewer_session_id 必须是真实 SubAgent 的 session_id，不可占位"。
