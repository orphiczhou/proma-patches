# 树形多Agent终局验证方法论 v1.0

> 融合「结构化文档多Agent终局验证方法论」+「树形会话执行体系」
> 适用：Proma 树形体系下对 Agent 产出文档的审计与迭代收敛
> 强制力：指挥官必须遵守本文全部条款，不得省略、合并、替代

---

## 一、定位

本方法论是**强制执行规范**，不是参考建议。任何在 Proma 树形体系下执行文档审计任务的指挥官会话，必须严格按本文执行。违反任意一条即视为审计不可采信。

融合了两个来源：
- **上游方法论**：「结构化文档多Agent终局验证方法论」（三阶段、四维审查、反事实攻击、循环收敛）
- **执行框架**：「树形会话执行体系」（tree-commander + tree-worker + tree-state.js）

---

## 二、铁律（不可违反）

### 铁律 1：审查必须并行多Agent

**原文方法论要求**：阶段一 4 个审查员并行，阶段二 2 个攻击员并行。

**树形执行要求**：
- 指挥官必须 Fork **不少于 4 个子会话**执行阶段一（每人一个维度）
- 指挥官必须 Fork **不少于 2 个子会话**执行阶段二（反向映射 + 反事实攻击）
- 禁止将多个维度合并到单个子会话
- 禁止指挥官自己充当审查员（"自己画靶自己打分"）
- 所有审查子会话**必须使用与指挥官不同的模型**（打破推理惯性；如指挥官用 deepseek-v4-pro，则审查员用 deepseek-v4-pro 亦可，但理想状态是交叉模型）

**验证方式**：tree-state.json 中 leaves 数量 ≥ 7（1 root + 4 审查 + 2 攻击 + 可选走查）

### 铁律 2：必须迭代到收敛

**原文方法论要求**：循环 1-3 轮，直至收敛。

**树形执行要求**：
- 第一轮：审查子会话产出问题列表 → 修正 Agent 统一修改
- 第二轮：重新 Fork 审查子会话做回归验证（只检查修改是否正确、是否引入新问题）
- 收敛判定（三个条件全部满足方可停止）：
  1. 当前轮次新发现的问题数 < 上一轮的 30%
  2. 无阻断级或严重级新问题
  3. 所有遗留问题都是"建议"级或已标记"待人类确认"
- 禁止一轮就 declare done
- 每轮结果必须写入 tree-state.json（milestones + events）

**验证方式**：tree-state.json 的 drift_log 或 audit_meta 中记录每轮问题数

### 铁律 3：反事实攻击必须独立

**原文方法论要求**：攻击心态与建设心态冲突，必须用独立 Agent。

**树形执行要求**：
- 反事实攻击子会话**不得**与四维审查子会话复用
- 反事实攻击子会话**不得**与产出文档的子会话是同一个
- 攻击简报中必须明确列出至少 5 个具体攻击场景（覆盖边界、结论逻辑、时间线）

**验证方式**：攻击子会话的 brief 中 `in_scope` 含具体攻击场景列表

### 铁律 4：修正后必须回归

每次修正完成后，必须重新启动审查子会话验证：
- 原问题是否已修复
- 修正是否引入了新问题
- 禁止"修正完直接 commit"

### 铁律 5：结论必须基于证据

- "通过"必须有可复现的验证路径
- "跳过"必须说明原因和替代方案探索记录
- "READY FOR RELEASE" 必须在收敛后方可声明
- 禁止在未提交 git 的文件中声明"READY FOR RELEASE"

## 三、标准执行流程

### 阶段零：指挥官规划

```
1. 读取本文（tree-audit-methodology.md）
2. 读取上游方法论（Agent生成文档审查方法论参考.txt）
3. 读取待审文档 + 上游文档
4. 初始化 tree-state（tree_id 自定）
5. 规划 leaf 结构（至少 7 个 leaf）
6. 为每个 leaf 编写 5 件套契约（brief/dod/report/autonomy/self_audit）
```

### 阶段一：四维交叉审查（Round 1）

```
指挥官 Fork 4 个子会话并行：

┌── C1: 一致性审查员
│    盯：报告与上游文档是否矛盾？用例计数可复算？测试环境与方案一致？
│
├── C2: 完整性/闭环审查员
│    盯：所有工具覆盖？错误用例？集成场景？跳过理由充分？性能数据完整？
│
├── C3: 规范性/格式审查员
│    盯：报告格式合规？严重度评级合理？结论不基于主观判断？统计表述不误导？
│
└── C4: 可验证性/证据审查员
      盯：关键声称有可验证证据？session ID 完整？时间戳可追溯？第三方可复现？

每人产出结构化问题列表：
  [审查员X] 问题ID | 定位(行号) | 严重程度(阻断/严重/建议) | 描述 | 修正建议

指挥官汇总去重 → 修正Agent统一修改 → 进入阶段二
```

### 阶段二：反向映射 + 反事实攻击（Round 1）

```
指挥官 Fork 2 个子会话并行：

┌── A1: 反向映射重构员
│    步骤：
│    1. 忽略报告原有分组和标注
│    2. 从每条内容反向提取它所覆盖的功能点
│    3. 汇总为功能清单
│    4. 将清单与上游文档逐项比对
│    5. 标记：遗漏 / 冗余 / 偏离
│
└── A2: 反事实攻击员
     两种攻击角色（同一子会话内串行）：
     
     角色视角攻击：
     - 以每个角色/用户视角提出 3 个"如果...怎么办"
     - 检查文档是否覆盖
     
     契约边界攻击：
     - 针对每条验收标准构造 1-2 个"刚好在边界外"的输入
     - 标记所有契约模糊点
     
     额外攻击维度（针对测试报告）：
     - 覆盖边界：单一频道/模型/workspace 是否足以支撑通用结论？
     - 结论逻辑：跳过=未覆盖≠通过；统计数据是否误导？
     - 时间线：声称的时间窗口与实际 session 时间戳是否吻合？

产出漏洞列表 → 指挥官汇总 → 修正Agent统一修改
```

### 阶段三：场景走查

```
指挥官自己（或 Fork 1 个子会话）执行：

1. 选定 1-3 条核心流程
2. 逐步走查：每一步是否在文档中有明确对应？
3. 标记"走不通"的步骤
```

### 循环迭代（Round 2+）

```
修正完成后：

1. 重新 Fork 4 个审查子会话（阶段一回归）
2. 重新 Fork 2 个攻击子会话（阶段二回归）
3. 判断收敛：
   - N_new < N_prev × 0.3？
   - 无阻断/严重？
   - 残留均为建议级？
   → 满足 → 进入最终步骤
   → 不满足 → 再次修正 → 再次回归
```

### 最终步骤

```
1. 修正Agent应用最后一轮修改
2. 最终 tree-state validate() 必须 ok
3. git add + git commit（含完整的 commit message）
4. 报告头部标注：审计轮次、审查子会话 ID 列表、收敛判定
```

## 四、tree-state 记录规范

### 必须记录的 leaf

| leaf_id | role | 说明 |
|---------|------|------|
| `{tree_id}-root` | root | 指挥官 |
| `{tree_id}-C1` | consistency | 一致性审查 |
| `{tree_id}-C2` | completeness | 完整性审查 |
| `{tree_id}-C3` | standards | 规范性审查 |
| `{tree_id}-C4` | evidence | 可验证性审查 |
| `{tree_id}-A1` | reverse-map | 反向映射 |
| `{tree_id}-A2` | counterfactual | 反事实攻击 |
| `{tree_id}-fix` | fixer | 修正执行（可选独立） |

### 每个 leaf 必须记录

- `milestones`：至少 M1（理解+规划）+ M2（执行+产出）
- `events`：至少 brief_echo + done
- done 的 `meta` 中必须包含问题数量统计

### 每轮迭代记录

在 tree-state.json 的 `_meta` 中追加：

```json
{
  "audit_rounds": [
    {
      "round": 1,
      "issues_found": {"blocker": 3, "severe": 6, "suggestion": 8},
      "issues_fixed": {"blocker": 3, "severe": 6, "suggestion": 6},
      "regression_issues": 0
    }
  ],
  "converged": true,
  "convergence_round": 2
}
```

## 五、常见违规及后果

| 违规 | 后果 | 检测方式 |
|------|------|---------|
| 只用 1 个子会话审查 | 审计不可采信，必须重做 | tree-state leaves < 7 |
| 一轮就结束 | 审计不可采信，必须重做 | audit_rounds 长度 = 1 |
| 指挥官自己做审查员 | "自己画靶自己打分" | 审查 leaf 的 session_id = root session_id |
| 修正后不回归 | 可能引入新问题 | 无 Round 2 记录 |
| 攻击员与审查员复用同一会话 | 攻击力度不足 | leaf 数不足 |
| 未 commit 就声明完成 | 结论未固化 | git status 检查 |

## 六、快速检查清单（指挥官用）

在 declare done 之前，逐项确认：

```
[ ] tree-state.json leaves ≥ 7
[ ] 阶段一：4 个审查子会话全部 done，产出结构化问题列表
[ ] 阶段二：2 个攻击子会话全部 done，产出漏洞列表
[ ] 阶段三：场景走查完成，无阻断点
[ ] 修正Agent已应用所有修复
[ ] Round 2 回归审查完成
[ ] 收敛判定通过（N_new < N_prev × 0.3，无阻断/严重新问题）
[ ] tree-state validate() = {ok: true, issues: []}
[ ] git commit 完成
[ ] 报告头部标注审计轮次和审查子会话 ID 列表
```

## 七、与原始方法论的关系

本文是「结构化文档多Agent终局验证方法论」在 Proma 树形会话执行体系下的**强制实例化**。原始方法论定义"做什么"，本文定义"在 Proma 里怎么做、怎么验证做了"。

两者冲突时以本文为准（因为本文考虑了 Proma 的具体执行约束：Fork 机制、send_message 通信、tree-state 记录、workspace=null 限制等）。

原始方法论文件：`Agent生成文档审查方法论参考.txt`
树形体系设计：`tree-commander-design.md`
