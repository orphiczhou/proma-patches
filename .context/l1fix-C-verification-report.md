### 攻击场景 3: 跨 Provider 实质性攻击

**构造**: "如果质疑者声称 T3 '跨 provider 切换' 实际上只是两个独立的单 provider 测试串在一起，并非真正的'切换'——因为测试中没有在同一 session 内切换 provider 再发消息，而是创建了两个独立 session 分别测不同 provider。"

**攻击执行**:

1. 原方案 10.3 的设计意图: "跨 provider 模型切换（glm→deepseek）" — 同一会话内切换模型
2. T3 实际测试方式: MiniMax 频道创建独立会话 A，DeepSeek 频道创建独立会话 B，各自 send_message
3. 真正的 "跨 provider 切换" 场景（同一会话内从 provider A 切到 provider B 发消息）并未被测试
4. v4 报告在 line 69-76 的描述是 "两侧均可正常创建会话并通信，跨 provider 切换无报错"，但未区分 "独立双 provider 可用性" 与 "单一会话跨 provider 模型切换"

**判定**: T3 测试验证的是 **跨 provider 可用性**（两个 provider 分别能创建会话并通信），而非原方案设计的 **跨 provider 模型切换**（同一会话内从 Provider A 的模型切到 Provider B 的模型）。报告的措辞 "跨 provider 切换" 存在轻微的语义偏移。

**但是**: 集成场景 2 的替代方案 (flash→pro 跨模型 Fork) 部分弥补了这一缺口 — Fork 操作确实涉及跨模型切换，只是两个模型同属 DeepSeek provider。真正的跨 provider 切换（如 MiniMax→DeepSeek 同一会话）在当前 MCP 架构下是否支持尚不明确。

**严重度**: 低 (非阻断 — 报告的 "已知行为不一致" + 集成场景2 已覆盖跨模型维度)
