好的。我们这几轮交互下来，确实走出了一条非常有效的路径——从单Agent产出，到四维交叉审查，到终局验证（反向映射+反事实攻击），再到循环修正。现在把这一整套方法论提炼出来，你以后检查任何文档都可以复用。

## 结构化文档多Agent终局验证方法论

> 适用对象：AI Agent产出的结构化文档（用户故事、PRD、架构设计、API规范等）
> 核心思想：用“攻击”代替“审查”，用“多维并行”打破“单一推理惯性”，用“循环收敛”逼近完整自洽

---

### 一、为什么需要这套方法论

单Agent产出文档的经典盲区：
- **推理惯性**：同一套思维链路难以发现自己的逻辑跳跃
- **维度塌陷**：产出时关注了A维度，B维度的矛盾就被忽略了
- **修正副作用**：改了一个地方，在另一个地方埋下新的不一致

这套方法论的解决思路是：**用多Agent团队从不同维度同时“围攻”文档，逼出隐藏问题，循环修正直到收敛。**

---

### 二、三阶段验证体系

```
阶段一：结构完整性审查     阶段二：逻辑严密性攻击      阶段三：场景走查
（找显性问题）             （找隐藏矛盾）             （验实战可用性）
       │                        │                        │
       ▼                        ▼                        ▼
  四维交叉审查            反向映射 + 反事实攻击      真实流程推演
  Agent Teams并行          Agent Teams并行           单Agent串行即可
       │                        │                        │
       ▼                        ▼                        ▼
  发现问题 → 修正          发现漏洞 → 修正           发现断层 → 修正
       │                        │                        │
       └────────┬───────────────┴────────────────────────┘
                │
                ▼
          循环1-3轮，直至收敛
```

---

### 三、阶段一：结构完整性审查——四维交叉

**目标**：找出显性错误——违反规则、逻辑矛盾、遗漏、格式问题。

**为什么是四个维度？**
这四个维度覆盖了一份结构化文档最常见的四类问题，且彼此独立，可以并行审查。少了会有盲区，多了会有冗余。

**四维定义**：

| 审查维度 | 核心问题 | 适合的文档类型 |
|---------|---------|:---:|
| **一致性审查** | 文档内容是否与上游文档（如PRD）存在矛盾？ | 全部 |
| **角色/职责闭环审查** | 定义的角色是否都有对应覆盖？职责是否越界？ | 用户故事、系统设计 |
| **规则符合性审查** | 是否遵守了方法论规则（INVEST、GWT格式等）？ | 用户故事、测试用例 |
| **契约/边界审查** | 验收标准是否可客观验证？边界是否覆盖？ | 用户故事、API Spec |

**执行方式**：
- Agent Teams同时启动四个审查员，每个只盯一个维度
- 每人产出结构化问题列表：`[审查员X] 问题ID | 定位 | 严重程度 | 描述 | 修正建议`
- 汇总去重后，由修正Agent统一修改
- 修正完成后，再次启动四个审查员做回归验证（只检查修改是否正确、是否引入新问题）

---

### 四、阶段二：逻辑严密性攻击——反向映射 + 反事实

**目标**：找出阶段一发现不了的隐藏问题——隐性遗漏、契约模糊、二次矛盾。

阶段一只能找出“违反明面规则”的问题。但一份文档可能所有规则都符合，却仍然存在致命的逻辑漏洞。阶段二用攻击心态来炸出这些漏洞。

#### 方法A：反向映射重构

**原理**：让另一个Agent从文档中“反向提取”功能清单，再与上游文档逐项比对。同一Agent既做映射又做比对会“自己画靶自己打分”，所以必须用独立Agent。

**步骤**：
1. 忽略文档原有的分组和标注
2. 从每条内容反向提取它所覆盖的功能/需求/接口点
3. 汇总为一份功能清单
4. 将清单与上游权威文档逐项比对
5. 标记：遗漏（上游有但清单无）、冗余（清单有但上游无）、偏离（都有但描述不一致）

#### 方法B：反事实攻击

**原理**：主动构造“如果发生X情况，文档能不能兜住？”的破坏性测试。需要“攻击心态”——和产出Agent的“建设心态”冲突，所以必须用独立Agent。

**两种攻击角色**：

**角色视角攻击**：
- 以文档中定义的每一个角色/用户视角
- 提出该角色最关心的3个“如果...怎么办”场景
- 检查文档是否覆盖这些场景
- 标记无法覆盖的场景

**契约边界攻击**：
- 针对每一条验收标准/契约/GWT场景
- 故意构造1-2个“刚好在覆盖边界之外”但属于合理预期的输入/行为
- 如果现有契约无法判断该输入是否合法——视为契约模糊
- 标记所有契约模糊点

**执行方式**：
- 反向映射和反事实攻击可以并行执行
- 反事实攻击中的两个角色也可以并行
- 汇总所有漏洞，按严重程度（阻塞/严重/建议）分级
- 修正后，对阻塞和严重级漏洞做回归验证

---

### 五、阶段三：场景走查

**目标**：验证文档在真实使用场景中是否“能跑通”，发现流程断层。

前两个阶段验证的是“静态质量”。但文档最终要支撑实际工作流。场景走查模拟真实路径，检查每一步是否有对应的文档支撑。

**步骤**：
1. 选定1-3条最核心的用户/系统流程（从上游文档中提取）
2. 逐步走查：流程的每一步，是否在当前文档中有明确的对应内容？
3. 标记“走不通”的步骤：该步骤需要的输入、决策、产出在文档中缺失或模糊

**适用判断**：
- 用户故事文档 → 走查快消型和长期迭代型两条核心流程
- API规范 → 走查一个完整的请求-响应-错误处理链路
- 架构设计 → 走查一个模块从启动到完成任务的完整调用链

**为什么场景走查放在最后？**
因为前两个阶段会导致文档被多次修改。如果在修改前做场景走查，发现的问题可能在后续修改中失效。放在最后，是对“最终版本”的实战验证。

---

### 六、循环策略

**核心原则**：每一轮验证后必须修正，修正后必须回归。循环的终止条件不是“跑了N轮”，而是“收敛”。

**收敛标准**：
- 当前轮次新发现的问题数 < 上一轮的30%
- 且无阻塞级或严重级新问题
- 且所有遗留问题都是“建议”级或已标记“待人类确认”

**建议循环次数**：

| 文档复杂度 | 建议循环 | 说明 |
|-----------|:---:|------|
| 简单（<10条内容） | 1-2轮 | 阶段一 + 一次回归通常足够 |
| 中等（10-30条内容） | 2-3轮 | 阶段一 + 阶段二 + 回归 |
| 复杂（>30条内容，多角色/多系统） | 3轮+ | 三轮都上，阶段三可能需要单独一轮 |

**注意**：不要无限循环。如果3轮后仍有严重问题，说明上游文档（如PRD）本身可能存在模糊之处，需要回到上游澄清，而不是继续在当层修正。

### 八、与不同文档类型的适配

这套方法论的骨架（三阶段）是通用的，但四维审查的具体维度需要根据文档类型调整：

| 文档类型 | 四维审查适配 | 反事实攻击重点 |
|---------|-------------|:---:|
| 用户故事 | 一致性(PRD)、角色闭环、INVEST、GWT契约 | 角色场景、验收边界 |
| 架构设计 | 一致性(PRD)、模块闭环、选型有理由、接口明确 | 故障场景、扩展场景 |
| API Spec | 一致性(架构)、端点完整、Schema可验证、错误覆盖 | 异常输入、并发场景 |
| 测试用例 | 一致性(用户故事)、覆盖P0、可执行、异常覆盖 | 边界输入、组合场景 |
