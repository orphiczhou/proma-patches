## 二、关键问题清单（P0 阻断，按修复优先级）

### 🔴 第一优先：版本/文档治理（系统性，影响全局）
1. **[B2-P0-1] API 文档版本剪刀差**：api-spec.md 已 v0.4（20 端点/66 错误码/6 接口类），但 agent-comm.md、events.md、frontend-backend-api.md 均基于 v0.3（16 端点/56 错误码）。导致 4 个 `project:*` IPC channel、10 个错误码、20+ 处"16端点"过期声明。
2. **[A1-P0-2] user-stories 版本链断裂**：`user-stories-v0.2.md` 文件名为 v0.2 但**内容实为 v0.6**（与 v0.6 文件逐字节一致），真正的 v0.2/v0.3/v0.4 缺失，可追溯版本链仅 v0.1→v0.6。
3. **[A1-P1-5] PRD v0.2 落后近 2 个月**：user-stories 已 v0.6 但 PRD 停在 v0.2，Q1-Q5 裁决、D-1/D-2 遗留项未回写 PRD。

### 🔴 第二优先：实现层阻断（C1）
4. **[C1-P0] 整库不可运行**：package.json 无 build/start 脚本、tsconfig `noEmit:true`、无 Electron main 进程入口，20 个 IPC 端点全部指向不存在的 handler。仅类型层面自洽。
5. **[C1-P0] 沙箱管理器完全缺失（0%）**：架构 §6 要求 L0+L1 沙箱，但 src/ 无任何沙箱文件；AI 生成代码可直接读任意文件、消耗主机资源。
6. **[C1-P0] 真 Agent 实现全部缺失**：wizard 仅 1/4 角色骨架，coder/judge 全部 stub（mock 3/2 函数），router 依赖的 AISession 真 LLM 对接未实装。

### 🔴 第三优先：测试流程阻断（C2）
7. **[C2-P0-1] Phase 2-4（S4-S13）测试规划完全空白**：test-plan §0.3 范围限定"快消型 MVP（S1-S3）"，10 个 Sprint 无任何测试章节——项目级最大测试债务。
8. **[C2-P0-2] 缺陷管理流程完全缺失**：209 用例产生的失败无流转机制（无严重等级、issue 模板、分配、验证、关闭准则）。
9. **[C2-P0-3] 被测实现判据不明**：sprint-note 自承"自修复 3 次失败判据未明 / Context Backfill 六步可跑无客观信号 / 快照线性回滚文件级实现略空"，直接卡住 §4/§5 用例的自动化判定。

### 🔴 第四优先：设计层阻断（A1/B2）
10. **[A1-P0-1] 实时并行协作 vs 文件系统交接的架构矛盾**：PRD §13.1 规定 Agent 间通过文件系统交接（无消息队列），但 §4.3/§6.1 要求需求分析师与 UI/UX 顾问"并行工作"、实时生成界面草图。文件系统无法支撑 <1s 级双向实时协同。
11. **[B2-P0-2] 前端缺 4 个 project:* IPC channel**：导致项目管理模块无法对接。
12. **[B2-P0-4] 2 个新增错误码未收录**：`SESSION_LOCK_CONTENTION`、`GUIDE_INTERNAL_JUDGE_FAILED` 不在 api-spec 错误码总表。

## 三、一致性交叉验证（多维度互证，本轮审计核心增量）

> 6 份独立报告在隔离环境下产出，但多处发现**跨维度互相印证**，显著提升结论可信度。以下为根审计者交叉比对得出的系统性规律。

### ✅ 交叉验证 1：文档版本漂移是**项目级系统性问题**
- A1 发现 PRD v0.2 ↔ user-stories v0.6 滞后 2 个月；
- A2 发现 UX 三文件依赖头标"user-stories v0.6"但实际文件是 v0.1；
- B2 发现 api-spec v0.4 ↔ 3 子文档 v0.3；
- C2 发现 test-plan §9 审查状态落后 sprint-plan 一个阶段、埋点 13 vs 14 不一致。
**结论**：各文档独立演进、缺少统一 SSOT 同步机制。**根因是流程而非内容**——建议建立版本基线锁 + 文档间引用校验脚本，一次解决 4 个维度的同类问题。

### ✅ 交叉验证 2：三条"全栈贯穿缺口"（PRD→Story→架构→实现→测试 全链路断层）
| 缺口 | PRD层(A1) | 架构层(B1) | 实现层(C1) | 测试层(C2) |
|------|----------|-----------|-----------|-----------|
| **工程模板可扩展性 §11.4** | 零 story 覆盖(P1-4) | `Project.template` 固定 enum 6 值无法承载插件(D8/P2-4) | 未实现 | **完全无测试**(C-01) |
| **分析看板 §12.6** | —(PRD有) | 缺数据聚合层架构承载(A3/D6) | 未实现 | **完全无测试**(C-03) |
| **沙箱 L0/L1** | — | 设计要求(§6)但缓解对AI生成代码不可靠(P1-4/D1) | **完全缺失 0%**(P0) | 有 4 用例(TC-BOUND-206~209)但被测物不存在 |

这三条说明：设计文档在"主轴功能"上链路完整，但在**远期/扩展性需求**上从需求到测试**整条断层**。修复时应成链推进，而非各维度孤立补。

### ✅ 交叉验证 3：设计描述失准 ≠ 实现错误（一处正向印证）
- B1（架构审计）发现 `fs.linkSync` "复制目录树"描述过度简化（fs.linkSync 不支持目录），批评为 P1-2 风险；
- C1（实现审计）却发现 snapshot-manager **实际实现正确**：递归 walk + 逐文件 linkSync + 同步 mkdir（完成度 95%，含 NTFS 阈值、两阶段提交、CWE-22 防御）。
**结论**：这是**文档准确性问题，不是实现 bug**——实现者比文档更严谨。但文档措辞仍需修正以免误导后续实现者（B1 P1-2 建议有效）。

### ✅ 交叉验证 4：基础设施层扎实，业务能力层空心（C1 ↔ C2/B1/B2 互证）
- C1：router（95%）+ snapshot（95%）两引擎成熟度极高，端口注入设计为后续替换预留扩展点；
- C2：test-plan 在 API 契约层（20 端点）、事件层、异常自愈层、权限边界层覆盖**优秀**——这些恰好对应已实装的 router/snapshot 基础设施；
- B1/B2：类型定义（coder/types 11 类型、judge/types 12 类型、error-codes 完整）严格对齐 api-spec/architecture。
**结论**：项目处于**"类型+接口+2核心引擎"高完成度骨架**（S1 末态），契约/类型/基础设施质量很高，但业务逻辑（真 LLM、Agent 角色、沙箱、可运行入口）几乎为零。骨架质量预示后续填充风险可控。

### ⚠️ 交叉验证 5：一处维度间**需对齐的分歧**
- A1（PRD）将"并行协作 vs 文件交接"定为 **P0 阻断**；
- B1（架构）将同一问题（并行降级为串行交替，A2/D9）定为 **P2 建议**并称"文档已自识别、属已缓解"。
**根审计裁决**：A1 的 P0 定级针对的是 **PRD 需求与所选交接机制的内在矛盾**（需求层），B1 的 P2 针对的是 **架构已用串行降级实现**（实现层）。两者不冲突——问题真实存在（PRD 要求真并行），架构的"串行降级"是权宜方案但体感未验证（B1 P2-3）。建议合并为单一追踪项，PRD 侧澄清"并行"的强度（真并行 vs 体感并行），架构侧补 UX 验证。

## 四、总体评价与建议路线

### 项目当前定位
**设计阶段（01-04）成熟度中上（7.0-7.5/10），可实现性高；但存在系统性文档版本漂移与若干远期需求全栈断层。实现阶段（src/）处于高质量骨架期（32/100），契约/类型/基础设施扎实，业务能力与可运行性为零。**

### 建议修复顺序（按阻断半径）
1. **立即**：修 API 版本漂移（B2-P0-1）+ user-stories 版本链（A1-P0-2）——建立 SSOT 同步机制，连带解决 A2/C2 的版本引用问题。
2. **S2 启动前**：补 package.json 构建/Electron main 入口（C1-P0）让项目可运行；澄清 PRD"并行"定义（A1-P0-1）。
3. **S2-S3**：实装沙箱 L0（C1-P0，安全关键）；补 Phase 2 测试骨架 + 缺陷管理流程（C2-P0）。
4. **S3 收口前**：补三条全栈断层（模板可扩展性 / 分析看板 / 沙箱）的设计-测试成链推进。
5. **持续**：P1 跨文档同步（文案/术语/编号统一）、interaction-spec 补 5 类交互节（A2-P1-1）。

### 审计方法学备注
- **多模型交叉的价值**：12 项 P0 中，B2(DeepSeek) 抓出版本漂移、C1(MiniMax) 抓出不可运行、A1(DeepSeek) 抓出版本链断裂——不同模型对同一项目暴露了不同盲区，单一模型审计会漏。
- **交叉验证的增量**：本总报告的"系统性规律"（如版本漂移、全栈断层）非任何单份报告所有，而是 6 份报告互证得出，这是树形多 worker 审计相对单 Agent 审计的核心优势。
